# Progreso del frontend de InvescticTrack AI

## Auditoría inicial

El catálogo tenía 47 entradas, con 14 marcadas como implementadas y 33 planificadas. El árbol de Git estaba limpio. El modelo tenía un solo rol, el acceso a proyectos admitía privilegios por departamento y administración tenía acceso general. El panel era compartido, crear una propuesta la enviaba inmediatamente y registrar un proyecto podía omitir la aprobación.

`Backend/InvestiTrackBack` y `Backend/proposal-service` contienen aplicaciones Spring Boot. El servicio de propuestas tiene entidades, repositorios y migraciones. La búsqueda en `Backend/`, `back/` y `ai-service/` no encontró un servicio REST operativo para el frontend. El contrato de `Backend/.agents/api-endpoints.md` declara OAuth/OIDC, autenticación Bearer, paginación por cursor y ETag bajo `/api/v1`. El transporte histórico del frontend espera cookies, `/auth/me` y objetos o listas directos.

## Integración institucional pendiente

El modo demo es explícito y utiliza datos ficticios. Con `VITE_DEMO_MODE=false`, el cliente histórico conserva el transporte en `VITE_API_URL` para sesión, consulta de usuarios, proyectos y propuestas. Esa compatibilidad se ejercita con respuestas simuladas en las pruebas de transporte. Las rutas que dependen de servicios nuevos informan que la integración está pendiente. El repositorio carece del servidor necesario para acreditar pantallas como `INTEGRATED`.

| Área                    | Contrato esperado bajo `/api/v1`                                                                                                                                                                                                                  |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Identidad               | OIDC institucional y `GET /me` con `displayName`, `roles`, estado y capacidades. Migrar de la sesión histórica por cookie al mecanismo de identidad confirmado.                                                                                   |
| Propuestas              | `GET/POST /proposals`, `GET/PATCH /proposals/{proposalId}`, `/history`, `POST /transitions` y asociación de archivos. El servidor crea el borrador y valida transiciones, campos y versión.                                                       |
| Evaluaciones            | `/proposals/{proposalId}/evaluator-assignments`, `/evaluations` bajo la propuesta, `/submission`, `/release`, `/evaluation-criteria` y decisión institucional mediante la transición de propuesta.                                                |
| Proyectos               | `GET/POST /projects`, `GET/PATCH /projects/{projectId}`, `/members`, `/progress`, `/history` y `/transitions`. El contrato atribuye la conversión a coordinación. En demo también puede iniciarla el investigador propietario tras la aprobación. |
| Actividades e hitos     | Colecciones `/projects/{projectId}/activities` y `/milestones`, detalle, edición, transiciones y `/evidence`; `GET /deadlines` para la agenda.                                                                                                    |
| Archivos                | `/documents`, `/document-uploads`, `/completion`, `/processing-status`, `/associations`, `/versions` y `/download-authorization`. Se necesitan almacenamiento privado, escaneo y descargas de corta duración.                                     |
| Asistente               | `/ai/conversations`, `/questions`, `/messages` y `/ai/sources/{sourceReferenceId}`. El servicio debe verificar acceso, recuperar documentos autorizados y resolver citas al abrirlas.                                                             |
| Reportes y cierre       | `/report-definitions`, `/report-jobs` y autorización de descarga. `/projects/{projectId}/final-report` y `/submission`, `/publications`, validación y transición de cierre.                                                                       |
| Administración y avisos | Colecciones de `/users`, `/roles`, `/deactivation`, `/audit-events`, `/notifications` y `/me/notification-preferences`.                                                                                                                           |

La integración debe confirmar la forma de respuestas para Zod, el manejo de `If-Match` y de claves de idempotencia y la autorización en servidor de cada recurso. La información de demostración puede inspeccionarse desde el navegador y se reserva a datos ficticios. El asistente demo carece de recuperación de contenido RAG y conserva hasta 50 respuestas por identidad en memoria. En navegadores sin IndexedDB, los archivos de demostración quedan en memoria durante la pestaña. Las validaciones de archivos de demo cubren tamaño, extensión, MIME y cabecera básica.
